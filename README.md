# Thread Pool в Rust: описание на основе примера с `rayon`

## Проблема, которую решает thread pool

Создание потока — **дорогая операция**. Каждый вызов `std::thread::spawn` влечёт за собой:

- **системный вызов** (`clone` в Linux) — переход в ядро и обратно;
- **выделение стека** — обычно 2 МБ виртуальной памяти на поток;
- **регистрацию потока в ядре** — планировщик ОС должен добавить его в очередь;
- **TLS (Thread Local Storage), дескрипторы, структуры ядра** — дополнительные накладные расходы.

Если задача **короткая** (например, умножить число на себя), тратить на неё отдельный поток — расточительно. Поток создаётся быстрее, чем выполняется сама задача.

**Thread pool** решает это: потоки создаются **заранее** (один раз) и **переиспользуются** для множества задач. Пул держит фиксированное число рабочих потоков, а задачи кладутся в очередь и распределяются между ними.

## Разбор кода

### 1. Создание пула

```rust
let pool = ThreadPoolBuilder::new()
    .num_threads(4)
    .build()
    .unwrap();
```

- **`ThreadPoolBuilder::new()`** — создаёт **конфигуратор** пула, но **не сам пул**. Это просто настройки.
- **`.num_threads(4)`** — указываем, что в пуле будет **4 рабочих потока**.
- **`.build()`** — инициализирует пул с заданной конфигурацией. Возвращает `Result<ThreadPool, ThreadPoolBuildError>`.
- **`.unwrap()`** — разворачиваем `Result` (в примере ошибки не обрабатываются).

После этого в памяти живут **4 потока**, готовых принимать задачи. Они не завершаются после каждой задачи, а ждут следующую.

### 2. Выполнение кода в контексте пула

```rust
let res = pool.install(|| {
    (0..1000)
        .into_par_iter()
        .map(|x| x * x)
        .sum::<i32>()
});
```

- **`pool.install(closure)`** — выполняет замыкание **в контексте пула**. Это означает, что все параллельные операции внутри будут использовать **именно этот пул**, а не глобальный.
- **`(0..1000)`** — диапазон чисел от 0 до 999.
- **`.into_par_iter()`** — превращает обычный итератор в **параллельный** (parallel iterator). Это ключевой элемент rayon.
- **`.map(|x| x * x)`** — возводит каждое число в квадрат. Выполняется **параллельно** на 4 потоках.
- **`.sum::<i32>()`** — суммирует результаты. Тип указан явно, потому что `sum` может вернуть разные числовые типы.

### 3. Результат

```rust
println!("Result: {res}");
```

Сумма квадратов чисел от 0 до 999:

$$\sum_{x=0}^{999} x^2 = \frac{999 \cdot 1000 \cdot 1999}{6} = 332\,833\,500$$

Вывод:

```
Result: 332833500
```

## Что такое `par_iter` и как rayon распределяет работу

`into_par_iter()` создаёт **параллельный итератор**. Rayon использует технику **work-stealing**:

- Каждый поток имеет **свою очередь задач**.
- Когда поток заканчивает свои задачи, он **«крадёт»** задачи у других потоков.
- Это обеспечивает **равномерную загрузку** без ручного распределения.

Именно поэтому `map` по 1000 элементам эффективно распределяется между 4 потоками: каждый берёт свою порцию, а когда заканчивает — помогает другим.

## Почему `install` важен

Без `pool.install(...)` rayon использовал бы **глобальный пул** (создаётся лениво при первом обращении). Явный `install`:

- **изолирует** вычисления в конкретном пуле;
- позволяет **контролировать** число потоков;
- даёт возможность иметь **несколько пулов** для разных типов задач.

## Когда ручной `spawn` оправдан

Ручное создание потоков через `std::thread::spawn` **не всегда плохо**. Оно оправдано для **долгоживущих сущностей**:

| Сценарий | Подходит `spawn`? |
|---|---|
| Фоновый логгер, который живёт всё время работы программы | ✅ Да |
| Отдельный цикл обработки I/O (например, чтение с сокета) | ✅ Да |
| Обслуживание долгого соединения | ✅ Да |
| Обработка 1000 коротких задач | ❌ Нет, лучше пул |
| Параллельная обработка массива | ❌ Нет, лучше rayon |

Логика простая: если поток создаётся **один раз и работает долго** — `spawn` нормально. Если поток создаётся **на каждую задачу** и живёт миллисекунды — это расточительно.

## Типовые решения в Rust

### 1. `rayon::ThreadPool`

Для **CPU-bound** параллельных вычислений:

```rust
use rayon::prelude::*;

let sum: i32 = (0..1000).into_par_iter().map(|x| x * x).sum();
```

Rayon автоматически использует пул потоков и work-stealing.

### 2. `tokio::runtime`

Для **I/O-bound** асинхронных задач:

```rust
#[tokio::main]
async fn main() {
    let handles: Vec<_> = (0..100)
        .map(|i| tokio::spawn(async move { /* ... */ }))
        .collect();
    
    for h in handles {
        h.await.unwrap();
    }
}
```

Tokio использует **асинхронный runtime** с пулом потоков и кооперативной многозадачностью.

### 3. Крейт `threadpool`

Лёгкий крейт для **фиксированного пула потоков**:

```rust
use threadpool::ThreadPool;

let pool = ThreadPool::new(4);

for i in 0..10 {
    pool.execute(move || {
        println!("Task {}", i);
    });
}

pool.join();
```

Проще, чем rayon, но без work-stealing и параллельных итераторов.

## Зачем нужен явный пул

Явный пул полезен, когда нужно **отделить горячие задачи от фоновых**:

- **Горячие задачи** — например, обработка HTTP-запросов — должны выполняться в **одном пуле** с приоритетом.
- **Фоновые задачи** — например, логирование, аналитика, сжатие — в **другом пуле**, чтобы не мешать горячим.
- **Изоляция** — если одна задача заблокирует поток, это не повлияет на другие пулы.

В Tokio это делается через **разные runtime**:

```rust
// Горячий runtime для HTTP
let hot = tokio::runtime::Builder::new_multi_thread()
    .worker_threads(4)
    .build()
    .unwrap();

// Фоновый runtime для аналитики
let cold = tokio::runtime::Builder::new_multi_thread()
    .worker_threads(1)
    .build()
    .unwrap();
```

## Сравнение подходов

| Подход | Когда использовать | Накладные расходы |
|---|---|---|
| `std::thread::spawn` | Долгоживущие потоки | Высокие (создание потока) |
| `rayon::ThreadPool` | CPU-bound, параллельные итераторы | Низкие (переиспользование) |
| `tokio::runtime` | I/O-bound, async | Низкие (переиспользование) |
| `threadpool` | Простой фиксированный пул | Низкие |
| Ручной пул | Специфические требования | Зависит от реализации |

## Ключевые выводы

1. **Создание потока дорого** — syscall, стек, регистрация в ядре.
2. **Thread pool переиспользует потоки** — создаёт заранее, не тратит на каждую задачу.
3. **Rayon** — стандарт для CPU-bound параллельных вычислений в Rust.
4. **Tokio** — стандарт для I/O-bound асинхронных задач.
5. **Ручной `spawn`** оправдан для долгоживущих сущностей (логгеры, циклы I/O).
6. **Явный пул** полезен для изоляции горячих и фоновых задач.

## Итог по вашему примеру

- `ThreadPoolBuilder` — конфигуратор пула.
- `.num_threads(4)` — 4 рабочих потока.
- `.build()` — инициализация пула.
- `.install(closure)` — выполнение кода в контексте этого пула.
- `.into_par_iter()` — параллельный итератор (rayon).
- `.map().sum()` — параллельная обработка и агрегация.
- Результат — сумма квадратов от 0 до 999 = **332 833 500**.

Код демонстрирует **правильный подход** к параллельным вычислениям: вместо 1000 отдельных потоков используется пул из 4 потоков с work-stealing, что даёт высокую производительность при минимальных накладных расходах.
